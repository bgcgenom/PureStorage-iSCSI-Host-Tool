1. Purpose and scope

The iSCSI Host Tool is a Pure Storage-specific Windows administration utility. It validates and configures Windows host prerequisites for Pure Storage iSCSI connectivity, discovers host IQNs, manages Pure host registration and host-group membership, builds a recommended host-to-array iSCSI connection plan, applies explicitly approved Windows iSCSI portal/session changes, and performs post-Apply verification.

Out of scope: the tool does not create volumes, connect or map LUNs, create CSVs, create or modify Pods, create or modify Protection Groups, build a Windows Failover Cluster, or add/remove storage paths to force compliance.

3. Recommended workflow

  1. Start the tool elevated.
  2. Run prerequisite checks.
  3. Enter or load Windows host names.
  4. Run Audit Hosts.
  5. If required, run Configure Pure Best Practices.
  6. Reboot hosts if the tool reports reboot required.
  7. Run Audit Hosts again after reboot.
  8. Add or reconnect one or more Pure arrays.
  9. Select the desired Host Group mode.
  10. Run Validate / Dry Run for Pure registration.
  11. Resolve blocked or conflicting rows and review Change Preview.
  12. Run Apply Pure Registration only when the validated plan is correct.
  13. Open iSCSI Connections.
  14. Select Build Recommended Plan or add manual exceptions.
  15. Run iSCSI Validate / Dry Run.
  16. Review Show Change Preview.
  17. Run Apply iSCSI Connections.
  18. Confirm hosts, arrays, and enabled paths show Applied / Verified.
  19. Export results and retain the log with the change record.

Configure Pure Best Practices

This action applies the supported host-level Pure Storage baseline to selected Windows hosts. It does not create storage objects or change array-side mappings.

Reboot: MPIO changes may require a reboot. The tool reports reboot-required state and does not silently reboot servers.
MPIO distinction: the global default policy is host-level configuration. Existing Pure devices may retain a per-device policy that differs from the host default. Per-device validation is separate from the host baseline.

5. Arrays

Arrays may be added during the current session or loaded from saved array definitions.

Saved arrays

Saved array definitions contain only non-secret connection metadata such as endpoint and array name. Credentials are not saved.

  • Credentials exist only for the active session.
  • Saved definitions are protected using Windows DPAPI.
  • Reauthentication is required after restarting the tool.
  • Connect Saved reconnects saved arrays using credentials supplied at runtime.

Array status

Validate / Dry Run and Apply require all arrays in the current scope to be connected. A disconnected or failed array blocks the operation.

6. Host Groups

The Pure registration workflow supports three Host Group modes:

ModeBehavior
No Host GroupHosts are registered individually. No Host Group membership is requested.
Create Host GroupThe named Host Group is created or verified and validated hosts are added as appropriate.
Use Existing Host GroupSelects an existing Host Group discovered from connected arrays.

When multiple arrays are connected, the existing-host-group selector shows group names that exist on every connected array.

If no array is connected, selecting Use Existing Host Group displays a message requiring an array connection first.

7. Validate / Dry Run

Validate / Dry Run is the required planning stage before Apply. It does not make Pure-side changes.

The validation gate requires a current successful Windows audit, a valid iqn.* for every audited host, at least one array, all arrays in scope connected, and no active conflicting operation.

StateMeaning
CREATEHost does not exist and the IQN is not already assigned.

BLOCKEDThe row cannot be applied until the conflict is resolved.
Any change to hosts, arrays, IQNs, Host Group selection, or other plan inputs invalidates the previous validation. A stale plan must be validated again before Apply.

8. Apply Pure Registration

Apply Pure Registration executes the validated host-registration plan after operator confirmation.

  1. Review the validation grid.
  2. Open Change Preview.
  3. Confirm Host, Array, State, Host Group, and Action are correct.
  4. Select Apply Pure Registration.
  5. Review the confirmation dialog.
  6. Proceed only if requested changes match the approved plan.
  7. Review post-Apply verification and the session log.
Do not treat confirmation as proof of success. Success requires the Pure write operations to execute and post-Apply verification to confirm the expected host, IQN, and Host Group state.

9. iSCSI Connections

The iSCSI Connections workflow configures Windows-side connectivity only after a successful Validate / Dry Run and explicit Apply confirmation.

Recommended Plan

Build Recommended Plan scans audited host IPv4 interfaces and connected Pure iSCSI target ports. It proposes same-subnet source-to-target mappings and resolves target IQNs from the selected Pure targets. Non-matching interfaces are excluded automatically. Manual mappings remain available for exceptions or non-standard topologies.

Validation

Each enabled path is checked for source-IP presence, TCP/3260 reachability, target portal state, target IQN, active session state, persistence, and duplicate/conflicting definitions. Existing correct configuration is reported as MATCH; missing configuration is planned as CREATE or CONNECT. Blocked rows prevent Apply.

Apply and post-verification

Apply may create Windows iSCSI target portals and persistent multipath sessions for the validated plan. After successful connection writes, the tool runs Update-HostStorageCache on affected hosts, then verifies portals, sessions, persistence, source/target addressing, and available Pure/MPIO runtime data.

Applied / Verified: after post-verification succeeds, affected host and array nodes display Applied / Verified, and enabled path result rows are marked Applied / Verified.
If no Pure LUNs are presented yet, the storage refresh is still safe. No visible Pure disks is informational and does not cause iSCSI Apply to fail.
Storage provisioning remains out of scope: this workflow does not create or map Pure volumes, initialize or format disks, create CSVs, or change Failover Cluster configuration.

10. Conflict handling

Conflict resolution is deliberately conservative. The tool does not silently overwrite or delete host definitions. Before destructive correction is allowed, the tool checks for conditions such as direct volume connections and Host Group membership. Unsafe conditions remain blocked.

Always confirm the identity of the host and IQN before replacing or removing an existing Pure host object.

11. Reboot workflow

When Windows configuration requires a reboot, the tool marks the host accordingly. Reboot actions are explicit.

  1. Wait for the host to return.
  2. Confirm WinRM connectivity.
  3. Confirm LastBootUpTime changed.
  4. Rerun Audit Hosts.
  5. Do not rely on the pre-reboot audit as current validation.

12. Exports

Export CSV and Export All preserve validation and change evidence. Exported information may include Windows audit results, Pure validation results, Change Preview, session summary, session log, and post-Apply verification status.

Exports do not intentionally include passwords, API tokens, or PSCredential objects.

13. Logging

The log is the primary detailed record of tool activity. Retain it when troubleshooting or attaching evidence to a change record.

  • Tool startup and prerequisite status
  • Array connection and reconnection
  • Validation invalidation
  • Windows baseline configuration
  • Pure registration confirmation
  • Pure host write attempts and results
  • Host Group actions
  • Post-Apply verification
  • Errors and blocked operations

14. Security

  • Passwords and API credentials are not stored in saved array definitions.
  • Saved array metadata is protected with Windows DPAPI.
  • Credentials are session-only.
  • Run the tool only as an authorized administrator.
  • Treat exports and logs as infrastructure administration records.

15. Troubleshooting

Validate / Dry Run is disabled

Check the validation banner. Common causes are stale Windows audit data, missing IQNs, no connected arrays, or an operation still marked busy.

Existing Host Group list is empty

Confirm at least one array is connected. With multiple arrays, only Host Group names common to all connected arrays are shown.

Saved arrays show Not Connected

This is expected after restarting the tool. Saved definitions do not retain credentials. Use Connect Saved and authenticate again.

Apply remains disabled

Resolve blocked validation rows and rerun Validate / Dry Run. Apply is intentionally disabled when validation is stale or unresolved conflicts remain.

Host audit fails

Verify DNS resolution, WinRM, administrative credentials, firewall rules, and that the target server is online.

Array connection fails

Verify DNS, TCP 443, credentials, PureStoragePowerShellSDK2, and that the account is authorized on the target array.

Reboot required remains visible

Reboot the affected host, wait for it to return, then rerun Audit Hosts.

16. Safety boundaries

The tool is allowed to:
  • audit Windows Pure Storage host prerequisites;
  • configure the approved Windows Pure baseline;
  • discover host IQNs;
  • connect to Pure arrays;
  • validate Pure host registration;
  • create or correct Pure host registration when explicitly approved;
  • create/use Host Groups when explicitly selected and validated;
  • create validated Windows iSCSI target portals and persistent/multipath sessions when explicitly applied;
  • refresh the Windows storage cache after successful iSCSI Apply;
  • reboot selected Windows hosts when explicitly requested;
  • export reports and logs.
The tool must not:
  • create volumes;
  • connect or map LUNs;
  • create CSVs;
  • create or modify Pods;
  • create or modify Protection Groups;
  • build a Windows Failover Cluster;
  • create storage paths outside the validated iSCSI connection plan;
  • silently overwrite conflicting Pure host objects.
